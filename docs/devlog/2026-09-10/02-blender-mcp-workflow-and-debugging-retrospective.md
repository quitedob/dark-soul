## 2. Blender MCP 在这个流程中承担什么角色

MCP 提供观察和执行入口；具体建骨、权重、导出规则保存在仓库 Python 中。这样做的原因是：可以在同一工作台上重复执行、修复规则，并由另外的工具检查导出的文件。

相关工具及用途：

| 工具 | 方法 |
|---|---|
| mcp__blender__get_scene_info | 确认当前场景和已有对象，再决定工作场景，避免先清空用户场景。 |
| mcp__blender__execute_blender_code | 在 Blender Python 环境加载仓库工作台，分步导入、建骨、绑定、导出和布置预览。 |
| mcp__blender__get_viewport_screenshot | 观察骨架是否贴合身体，四肢、尾巴、衣摆和装备在姿态变化中是否合理。截图是检查入口，不是全部验收。 |
| mcp__blender__get_object_info | 适合进一步检查指定对象；本文把它列为当前可用的补充检查方式，不据此声称历史上每个模型都调用过。 |

当前工具描述要求把用户的原始目标作为 user_prompt 传入。长任务保持目标一致，技术子步骤放到 code 或执行说明中，不把“现在导出一下”伪装成用户原话。工具版本和参数可能变化，使用时应以实际暴露的 schema 为准。

本轮场景生成没有依赖 PolyHaven、Sketchfab、Hyper3D 或 Hunyuan3D 下载/生成模型。可调用某个工具，不等于这次工作使用了它。

### 2.1 交互式工作台的操作顺序

1. 读取场景信息，保留用户原场景。
2. 从未蒙皮的 originals 导入一个模型，建立独立工作场景。
3. 运行建骨和绑定逻辑；记录骨名、父子关系、网格归属、混合权重数量和误差。
4. 先导出 staged GLB 和可编辑 Blender 场景，再建立缩放后的检查展示。
5. 获取静止截图；旋转实际非根骨，观察关节和附属物，再恢复姿态。
6. 导出的 GLB 交给独立校验器和 Godot 验证。
7. 只有文件、截图、报告对应同一批字节时才发布。

下面是按当前工作台接口整理的 MCP execute_blender_code 中的 Python 示例，展示调用关系；本次写文档没有执行它：

~~~python
import importlib.util
import sys

path = "E:/godot/darksoul/tools/rig_glb_models.py"
spec = importlib.util.spec_from_file_location("glb_rig", path)
rig = importlib.util.module_from_spec(spec)
sys.modules["glb_rig"] = rig
spec.loader.exec_module(rig)

# 已存在的 originals 不会被 prepare() 覆盖。
inventory = rig.prepare()
wb, report = rig.build("bosses/03-Jade-Faced-Fox-NineTails.glb")
print(report)

# 仅用于交互式 Blender 的视口检查。
rig.show_grid([wb], columns=1, pose=False)
~~~

执行这一段之后才请求视口截图。姿态检查应是另一步。不要把长时间的全库重建、导出、截图和发布塞进一个难以恢复的 MCP 调用。

prepare() 只保证不覆盖已有 originals，并不会自动证明新备份仍是未蒙皮原件。如果 originals 丢失，而 out 已经转换过，应先恢复真正的原始备份，不能把当前 out 重新复制后冒充原始基线。

一个重要细节：show_grid 会为展示建立容器、调整模型的显示位置和缩放。它不是生产模型的单位转换。生产导出先完成；不能把展示用的缩放继续当作源模型重新发布。

### 2.2 为什么后来用后台 Blender

批处理需要固定起点、可预测退出码和不会污染用户场景的运行方式。后台进程采用：

~~~powershell
& 'E:/blender/blender.exe' --background --factory-startup --python-exit-code 1 --python tools/rig_glb_batch.py -- --prefix review-example bosses/03-Jade-Faced-Fox-NineTails.glb
~~~

这是可复用的单模型批次示例，执行会产生新的 staged 和检查文件；不是只读命令。

参数分别解决：

- background：在独立进程执行。
- factory-startup：避免用户当前 Blender 文件和偏好状态影响批次。
- python-exit-code 1：Python 失败应反映在退出码中。
- prefix：把一次批次的图像与报告分开。
- 明确模型路径：避免根据模糊名称误改整个库。

部分场景生成器会清理它所启动的初始场景，因此应在这种独立后台进程运行，不能随意把整段生成器搬进用户正在编辑的 Blender 文件。交互式 MCP 工作台的“保留原场景”和一次性生成器的“清理临时进程”是不同约定。

## 3. 先判断问题属于哪个层

用户看到的是“武器不对”“场景没有建模”“视角有偏差”，但同一种表象可能来自不同层。我采用的分层检查如下。

| 层 | 核心问题 | 本项目例子 |
|---|---|---|
| 文件与库存 | 实际文件是否存在、是哪个版本、是否已经发布？ | out 有文件，但 skins=0；后来动画 staged 已齐，游戏副本和清单却没更新。 |
| 几何与材质 | 模型形状、法线、UV、材质、贴图和单位是否正确？ | 九尾尾链中心线、Blender 法线变化、地板共面闪烁。 |
| 骨架与动画 | 真正有顶点权重吗？哪根骨驱动哪个部件？ | 披肩挂错头骨、刚性部件错误混合、武器子树丢失骨架。 |
| 坐标与时间 | 变换属于哪个空间？动画与攻击判定用什么时钟？ | 手部握持轴、骨骼“global”并非世界、挥砍晚于命中窗口。 |
| 物理与导航 | 玩家真的能走、跳、到达出口和绕开障碍吗？ | 湖路尽头旧栏杆、迷宫出口虚空、敌人卡在导航首点。 |
| 状态与生命周期 | 重试、死亡、卸载、存档重载是否恢复一致？ | 旧场景危险区残留、导航排队丢失、奖励重复发放风险。 |
| 显示与平台 | 实际窗口、相机、浏览器权限是否符合预期？ | 固定 1280 viewport、小窗口卡片、首次 Pointer Lock 被拒。 |

检查顺序通常从库存和实际运行版本开始。运行错了旧导出，后面的截图、参数调整和模型修改都可能针对错误对象。

## 4. 86 个模型：真实蒙皮如何建立

### 4.1 不把“有骨架节点”当作完成

初始 out 中 85 个 GLB 没有 skin；另有 templateweapons 使范围达到 86。已有运行时 PartRig 挂件不能替代 GLB 文件内的蒙皮。

真实交付需要同时存在：

- Armature / Skeleton 的关节层级。
- skin 的 joint 引用和逆绑定矩阵。
- 网格上的 JOINTS_0 与 WEIGHTS_0。
- 正确的网格—骨架关联。
- 静止时保持原形，非根骨变化时顶点真实变形。

仅旋转模型根节点，整件模型都会移动，无法证明蒙皮有效。工作台把根保持不变，对已加权的分支施加姿态，并比较 evaluated mesh 的实际顶点位移。后续专项还做独立分支检查，避免“有一个网格动了”掩盖其他部件绑错。

### 4.2 从已有几何与祖先关系确定归属

项目已有明确部件和命名层级，因此采用“几何位置 + 原始枢轴 + 祖先关系 + 针对性规则”。

- 肩、肘、手优先使用原来的关节枢轴。
- 没有独立手网格时，仍需虚拟手骨承载武器。
- 腰的位置从躯干推导，不让周围漂浮特效影响包围盒。
- 头盔饰片跟头，肩甲跟肩臂，背旗跟躯干，地面灼痕留在根。
- 武器从完整祖先关系判断所属手，不能只看叶节点名字。
- 生物、人形、机械与道具分别处理，不统一套人形骨架。

真实反例是 elbow 中含有 bow。早期子串规则把肘误认为弓；修正为词边界和上下文判断。同样，sash_tail 是衣带，不是动物尾巴；刑天没有头，盲钟没有人形腿，源码中的名字也不一定准确描述实际模型朝向。

相关实现：[骨架工作台](../../../tools/rig_glb_models.py)、[生物专项](../../../tools/rig_glb_creatures.py)、[人形专项](../../../tools/rig_glb_humanoids.py)、[道具专项](../../../tools/rig_glb_props.py)。

### 4.3 刚性与连续表面采用不同权重

金属甲片、武器硬件和钟体适合单骨刚性权重：部件跟随关节，但不弯曲。

躯干、袍摆、披肩、尾巴、绳索等连续表面适合相邻骨混合。在初始通用链上，将顶点投影到轴或曲线，得到链上的位置，在相邻两骨间插值；最多两个影响是该工作台基础绑定的取舍，不是所有角色蒙皮的通用上限。

原因是这批模型以分块低多边形几何为主，需要可解释、可检查的基础绑定。复杂肩部体积保持、手指、布料约束和极端姿态仍需要更细的动画美术处理。

### 4.4 九尾为什么需要单独修复

第一版虽然存在尾骨，数值检查也能观察到变形，但骨链沿直线排列，实际尾巴却是弯曲管状网格。骨数通过不等于骨架贴合模型。

修复从实际尾部网格的 UV 环恢复弯曲中心线，沿曲线重排每条尾巴的关节；九条尾各有独立六段链，尾环刚性跟根，尾簇跟末段。最终九尾为 72 骨、18 个混合网格，静止误差约 4.49e-7，非根骨位移约 0.314。

这解决了基础尾链贴合和归属，没有据此宣称九尾的大幅扫击、尾间碰撞和奔跑动画都已完成美术精修。

## 5. 保护原资产：法线、材质与发布

### 5.1 为什么“顶点数量一样”不够

导入可能合并重复顶点；严格要求顶点索引和数量原封不动，会错误拒绝等价几何。反过来，只比较包围盒或顶点云，又会漏掉反向三角形、UV 清零和法线翻转。

独立校验后来改为比较有方向的三角形角点，包含：

- 世界静止位置。
- 全部 UV 集。
- 法线。
- 材质归属。
- 相同三角形的重复数量。

允许循环调整同一三角形起点、顶点去重、重编号和有限浮点误差；不允许把反向绕序当成一样。

### 5.2 Blender 导出为什么会改变法线

加强校验后发现，部分 capsule/cone 极点在进入 Blender 自定义法线存储时已产生差异，问题并不是绑骨之后才出现。一个实际样本从 (0,-1,0) 变为约 (0.019504,-0.999796,-0.005201)，偏差约 1.1566°。

处理方式：

1. 保留导入器解码出来的原法线，存入 POINT 属性 _rig_source_normal。
2. 导出时使用该属性，沿原生 skin/world/Y-up 转换链处理。
3. 临时适配器在 finally 中恢复，不修改用户安装的 Blender 插件文件。
4. 对旧 .blend 的法线修复，先证明顶点及三角形角点对应，再对比修复前后的骨 rest transform 和全部权重指纹。

19 项旧问题中，18 项保持骨架和权重指纹不变；Divine Marksman 因早期没有保存 .blend，实际采用从原件重建。两者不能都称为“只换法线”。

这个适配器针对当时观察到的 Blender 5.2 导入/导出实现，并显式拒绝 morph target 情况。未来升级 Blender 要重新验证，不能假设内部接口永久不变。

实现：[法线保留](../../../tools/preserve_blender_normals.py)、[旧骨架法线修复](../../../tools/repair_rig_normals.py)。

### 5.3 材质不是只检查图片数量

发现过 Blender 把纹理 minFilter 从 9728 改成 9984。采样后处理只改 GLB 的 sampler JSON，不重写网格、骨架或图片字节。

独立检查还包括逐材质贴图 SHA256、贴图映射、sampler、PBR 参数及扩展值。图片数量减少可能只是重复对象合并，图片数量相同也可能是内容被替换。无纹理模型和基础 PBR 相同但 clearcoat 不同的材质同样需要正确区分；无法消除歧义就失败，不随意配对。

### 5.4 原件、候选、发布和游戏副本分开

| 位置 | 含义 |
|---|---|
| build/glb-models/rigging/originals | 未蒙皮原件；重新生成读取这里。 |
| build/glb-models/rigging/staged | 候选导出；有文件不代表已经完成。 |
| build/glb-models/rigging/blend | 可编辑工作场景。 |
| build/glb-models/rigging/reports、screenshots | 与指定文件绑定的数值和视觉证据。 |
| build/glb-models/out | 已通过发布流程的蒙皮基线。 |
| build/glb-models/animation | 从基线继续产生的动作、报告和动画导出。 |
| game/assets/models | 真正被游戏加载的副本。 |

发布工具验证文件哈希、报告、截图和 Godot 证据，检查输入在验证到发布之间没有改变，并保留旧文件。它检查的是提交的证据一致性，不可能仅凭 JSON 证明“人确实认真看过截图”。

逐文件临时写入和错误回滚也不等于跨整个库的原子事务：进程被强制终止或并发读取仍可能看到中间状态。因此发布/同步期间需要串行化写入和引擎导入。build 被 Git 忽略，备份不能只依赖 Git。

实现：[发布工具](../../../tools/publish_rigged_glbs.py)、[独立 GLB 校验](../../../tools/validate_skinned_glbs.mjs)、[Godot 批次验证](../../../tools/verify_rigged_glb_batch.py)。

## 6. 有蒙皮、能播放、有正确玩法是三个阶段

09-08 完成的是 86 个真实蒙皮 GLB，不能从中推导出正式动作已经接入游戏。

09-09 检查发现：动画目录中已有 86 个模型、761 个原创建模适配关键帧 clip，而游戏 GLB 仍是静态副本，model_actions.json 缺失。修复重点是验证和接入，不是重做蒙皮。

同步工具验证基线哈希、动画库存和部件定义，安装到 game/assets/models，生成动作元数据及 124 个可提取部件定义，并保留原有 import UID。静态 out 基线与动画游戏副本分别保存。

另一个运行时问题是：拿到武器子节点后释放原场景，会同时丢失 skin 依赖的共享骨架。因此选择 Sword、Shield、左右斧等部件时，保留整个骨架，只隐藏未选网格。验证要让目标部件实际播放动作，而不是只检查节点还在。

这些 clip 是 Blender 管线烘焙的原创建模适配原地动作，不是 mocap，也不是远程生成的拼接动画。游戏仍负责角色位移。动作存在、状态机选中、骨骼实际更新、武器正确跟随和命中时序一致，都需要分别检查。

## 7. 动作拼接前置：先明确空间与时间

[09-08 姿态采样记录](../2026-09-08/05-motion-stitch-pose-prerequisites.md) 完成的是本地数据准备。没有调用远程 stitch 服务，没有生成过渡动作，也没有把静态骨架假装成时间序列。

最容易出错的概念是 Godot 的 bone global pose：它相对 Skeleton3D，不直接是世界坐标。

~~~text
bone_world = skeleton.global_transform * skeleton.get_bone_global_pose(index)
~~~

外层角色放置节点与内部动画根骨也不同。前者决定实例在场景的位置，后者可能带有动作中的位移。把 Root/Hips 平移剥离过的游戏动作，无法重新采出原始根运动。

髋部朝向采用明确公式：

~~~text
axis = left_hip_world - right_hip_world
axis.y = 0
forward = normalize(cross(normalize(axis), world_up))
yaw = atan2(forward.x, forward.z)

0 -> +Z
+PI/2 -> +X
PI -> -Z
-PI/2 -> -X
~~~

当文字示例与公式冲突时，记录冲突和采用的约定。交换左右髋会产生 PI 翻转，不只是改正负号。骨名含糊、镜像/奇异变换、退化髋轴等情况直接报错。

采样临时复制动作、禁用循环和非变换轨道，避免 seek 执行攻击、音效或方法事件；采样前重置稀疏通道，完成或失败后恢复骨姿态和节点变换。1 米连接示例来自实际采样和实例位置调整，不是硬编码骨盆高度；这些数据也不能单独证明脚底接触或无滑步。

## 8. 29 关建模：结构先于装饰数量

### 8.1 把剧情要求转成可检查的布局

先读 [主线](../../story/main-story.md)、[世界观](../../story/lore.md)、[章节桥接图](../../story/chapter-bridge-map.md) 和章节详述，再为每关列出：

- 入口、出口、主路径、支路与可选区。
- 标志建筑和剧情证物。
- 普通敌人的角色、朝向、警戒范围、巡逻或伏击点。
- Boss 竞技场中心、入场边界、互动点和破坏物。
- 地面高度、坡道、净空、遮挡和相机可见性。

例如军营需要囚笼、看守、材料炉和军令桌；婚礼场景需要花轿、灯笼与队列；镜湖需要水亭、读镜点和真/假道路；铸魂者纪念区需要九位陨落者与三位生者，不能做成十二座含义相同的墓。

模型、碰撞、敌人和交互点来自同一空间计划，避免“美术把门画在这里，玩法入口却在另一处”。

### 8.2 为什么采用首关专门建模 + 五章模块库

首关需要明确的山门、回廊、侧殿和远景层次，因此由 build_awakening_temple.py 构建完整建筑体系。其记录规模为 245 个相连六米单元、8,820 平方米可行走面积，整体范围 102×150 米。

其余关卡使用五套主题组件，每套八类：Floor、Bridge、Rail、Column、Gate、Landmark、Rock、ArenaCover。另有五套剧情 GLB、46 种独立部件、186 个材质网格、209,778 个三角形，约 10.55 MB；当前 29 关有 211 处静态剧情布置、86 个普通敌人。

这样的取舍便于跨关修复同一种地板、桥、栏杆和碰撞，同时通过不同拓扑、标志建筑及剧情道具区分关卡。重复组件仍然存在；这不是逐关高精度手工雕刻，也不把组件数量当作美术质量的充分证明。

源码：[首关生成器](../../../tools/build_awakening_temple.py)、[环境组件](../../../tools/build_campaign_environment_kits.py)、[剧情模型](../../../tools/build_campaign_story_props.py)、[剧情布置](../../../game/scripts/data/campaign_scene_dressing.gd)、[敌人布局](../../../game/scripts/world/campaign_encounter_layout.gd)。

### 8.3 单位、坐标、材质和碰撞约定

生成器按 Godot 米制、Y 向上描述尺寸，构造 Blender 顶点时一次转换为 (x,-z,y)，glTF Y-up 导出回到目标约定。部件根变换保持单位，脚底零点明确，剧情部件正面按 -Z 约定。导出后读取实际 GLB 包围盒核对，不能只相信生成参数。

同材质部件合并，运行时用导入的真实网格批量绘制。地面和坡道的真实物理形状负责行走；开放式建筑用墙、柱等实体的导航代理，不能用一个包围盒盖住整个门洞。远山参与可见碰撞与否按用途处理，不能把全部远景都送进可行走导航烘焙。

颜色先检查 sRGB/线性转换及实际 Godot 光照。Blender 中合适的颜色不保证 WebGL 游戏中合适；曾出现天界过曝、血铁偏红、侧殿过暗，需在最终渲染链调整。

## 9. 地板和桥条纹：从画面追到真实 GLB

Chrome 在 04_01 等区域看到明显条纹。先固定同一站位和相机做前后对照，再检查导出的 POSITION/index 数据，而不是凭画面一开始就归因给抗锯齿或阴影。

原因是不同材质的表面共面：

- Bridge 的底板、板条和铆钉顶面原先都到 0.14 米。
- Floor 的石面和金属装饰也在争夺同一深度。

修复把 Bridge 的深色面、板条、铆钉顶部分别分开到约 0.02、0.12、0.14 米；Floor 石面降到 -0.012 米，装饰最高到 0。整体组件包围盒和物理边界保持不变。

检查直接比较同一 Y 平面上跨材质水平三角形的二维相交面积。五套组件共十个 Floor/Bridge 的共面重叠归零，其余三十种部件的属性、索引及材质哈希不变。再回到 Chrome 的相同观察点检查条纹消失。

证据：[真实 GLB 表面审计](../../../build/story-campaign-20260910/chrome/kit-surface-after-audit.json)。它是几何证据，不是引擎执行日志；两者分别保存。

## 10. 武器视觉偏差：分别检查轴、骨架和攻击时钟

完整问题链见 [武器时序记录](../2026-09-09/04-weapon-swing-visual-timing.md)。

### 10.1 握柄轴和跟随空间

Manny 的手骨 +Y 沿腕到指根，+Z 横过掌心。原实现把武器长轴映到错误的掌面方向，产生握持偏差。修复对齐握持轴，保留左手镜像和盾牌自己的校正；八个内嵌职业继续使用自身手骨约定。

跟随逻辑使用已经求值的 hand.R/L 或 DEF-hand.R/L，将骨姿态从 skeleton/world 转到 BodyYaw 空间，避免把不同空间的 Transform 直接相乘。换身体时保留装备节点，重新解析手骨；死亡动画也要继续更新手部装备。

### 10.2 刀光必须来自当前可见武器

原先固定刀光长 1.05 米，但当时模板剑缩放后的尖端只有约 0.54088 米。改为换装时读取可见网格顶点并缓存实际尖端，刀光由握点和尖端构成，包含武器 pivot 的朝向。

这个数值属于当时的模板剑，不能推广为所有武器的统一长度。

### 10.3 动画不能只整体加速

Manny 原直剑 clip 约 1.166667 秒，主要挥砍在 0.525–0.700 秒。直接套占位命中时刻，会出现伤害已发生但身体还在抬手。

修复将前摇、挥砍、收招三个区段分别映射到 AttackData 的时长；在边界插入原始插值姿态，缓存副本而不改源动画。命中结束和连击开放使用独立 method 轨，防止同时间 key 相互覆盖。

连击窗口需要整次攻击的经过时间，不能只读每个 FSM 阶段重置的局部时钟；下一段还要真正重启动画。

### 10.4 真实动画和程序化补偿不能重复生效

Chrome 慢动作发现收招时剑尖跳动：时序副本叫 combat/light_attack_timed，旧代码只把 real/ 前缀识别成真实动画，因而叠加了程序化转剑。

修复改为明确的真实姿态元数据。存在真实身体动作时只跟手骨；缺失动作时才允许回退。重击暂时复用现有真实直剑动作并按各自攻击时长重定时，不假称新增了独立重击素材。

另一个遗漏来自测试入口：直接传完整武器技数据的测试通过，玩家实际 F 键却经过缺少 stance_animation 的旧工厂。把测试改为真实 _try_style_skill() 路径，才发现并修复 T pose 回退。

### 10.5 真正独立的换武器

X 轮换三个右手兵器栏，I 打开装备菜单。它们保留身体、职业和左手装备，使用所选兵器的数据。Tab/旧职业键改变整套职业配置，不能算作独立武器切换。

存档恢复先还原身体/职业，再恢复武器栏，过程中抑制中间自动保存。检查除“换成功”之外还覆盖忙碌时拒绝、栏位分配、重开菜单、身体身份和保存恢复。

最终武器栏契约 897 项，装备姿态契约 1,539 项；Chrome 用实际 X/J 确认战斧选择、身体挥动和活动命中窗口。慢放通过 Engine.time_scale，未 seek 或直接写骨姿态。

## 11. 相机与倒置移动：修复实际几何关系

### 11.1 先区分隐形边界与可见墙

出生点身后的隐形边界曾把 SpringArm 挤进身体。隐形玩法封界允许相机穿过，但保留角色碰撞；可见墙仍阻挡相机。相机 RID 排除列表需要在创建、复活和换关后正确刷新。

锁敌俯仰曾有符号错误，用 Camera3D 实际投影检查玩家头部、目标高低和侧向位置。解锁后的臂长恢复不应被短暂回正计时器或手动旋转提前中断。

### 11.2 可见墙很近时，身体不能盖住画面

即使 SpringArm 碰撞完全正确，镜头被压到角色内部仍会遮满画面。按实际 Camera3D 到 rig 的距离，在小于 1 米时隐藏当前身体根，超过 1.25 米恢复，区间提供滞后，避免临界距离闪烁。

保留原可见状态，用弱引用处理换职业后销毁的旧身体，不暂停动画，也不改变碰撞、装备选择或原本隐藏的子部件。

Chrome 精确复查：05_05 近墙实际臂长约 0.416 米时身体隐藏；实际 W 行走 47 帧离墙后臂长恢复 5.2 米、身体重新显示。原生 76 项还覆盖换身体、倒置和动画继续播放。

### 11.3 地面直接倒置，不能绕脚底把胶囊翻进地板

旧翻转围绕角色原点，原点靠近脚底。倒置的一瞬间胶囊进入原地板，角色卡在地板下面；此前把角色先放到空中再测试，会绕开真实触发条件。

修复顺序：

1. 保存 body_collision 的世界中心。
2. 修改 up_direction 和角色倒置旋转。
3. 根据中心前后差值平移角色，保持胶囊世界中心不变。
4. 让真实重力将角色带到另一表面。

测试从实际站立状态按 E 开始，不再在翻转后写位置或速度。Chrome 四个锚点依序完成、HP 100，最终恢复正常重力；原生移动契约 17 项、五关机关总回归 687 项提供补充验证。

## 12. 场景通路：到机关终点还不等于能离开

这次最有价值的反例，是“机关进度完成”但玩家还卡在旧场景的边界。

### 12.1 镜湖

真实输入已经走完五段石路，complete 为 true，但再向前卡在 z≈-86.22。原场景旧栏杆未打开，后方也缺通往原岸的支撑。

修复在 x=6 补 z=-90、-96、-102 的地面，打开对应共享栏杆，并保留卸载时还原状态。最终 Chrome 从一次入口定位后，真实 E 读镜、WASD 走五段路，继续到原岸 z≈-113.315，HP 100。

证据保留两个尝试：第一次没读镜，即使踩到路面也还是进度 0；只有 completedRoute 记作完成，不能把走过相同坐标混同为解谜成功。

### 12.2 九尾迷宫

真实 E 答完三题，旧栏杆仍把角色挡在 z≈-68.22，而完成条件需要继续向南。出口更远处还存在没有地面的区段。

修复补中央 z=-78、-84、-90、-96 的四格，并把三种最后通道汇入原有道路。原生对九种配置逐题 E/WASD 验证，Chrome 针对配置 0 实际走到 z≈-107.121。

九种原生配置通过不能写成“Chrome 手动走完九种”；两套证据的范围分别列出。

### 12.3 共享接缝与合理阻挡

_fill_floor 在添加实体地面时，检查相邻实体格并打开共享的旧护栏，修复新旧区域之间的内部阻挡，包括 05_04 扩建庭院。外侧护栏和镜湖假地板不应一起移除。

另一方面，婚礼路线遇到真实灯笼和单向近路门时，先核实设计，再从允许通路绕行，不为了让测试直线通过而删掉剧情物或合法门禁。

最终回归覆盖入口、机关、出口、试炼获胜后的返程和卸载恢复。婚礼专项的主路通行证据不冒充完整护送任务输入通过。

## 13. 敌人、弹体与导航：使用真实运动反馈

### 13.1 敌人位置不仅是出生点射线

为每个 content_id 和重复序号指定守卫、伏击、远程、精英或巡逻角色，提供位置、朝向和路径。这样重排生成数组不会随机改变分工。

先检查胶囊脚印和地面支撑，再让敌人实际巡逻、追击和返回。曾有敌人出生时有支撑，运行后自己走出台边持续下落；移动时增加前方支撑检查，斜向边缘保留可通行分量，同时保留重力及合法击退坠落。

灰岸被动灵魂、治疗反应和 Boss 惩罚还要遵守敌对状态、入场条件、距离与视线。

### 13.2 导航有路径，角色仍可能不走

烘焙路径点比脚底高约 0.5 米，原先 0.35 米到达容差导致角色在首点抖动。将默认容差改为 0.7 米，并让未交战巡逻使用自身路线。这个改动由实际路径和角色位置差值支持，不是盲目提高移动速度。

离开机关场景后，又出现 refresh_queued=true、bake_requested=false。原因在排队回调生命周期；改成独立物理帧定时回调，避免共享单次信号连接丢失，并复查换关和销毁期间的队列。

导航烘焙应使用当前实际静态碰撞来源。早期为了导航生成的可见辅助平面曾盖住正常地面；删除辅助平面，等待地图注册并明确提交实际烘焙网格。

### 13.3 弹体不能只在安全相切点查询

弹体碰撞旧逻辑在“尚安全”的接触位置取重叠对象，可能漏掉玩家或掩体；贴墙生成还可能一开始就处于重叠状态。

修复查询首次不安全接触点，并处理初始重叠。原生测试不仅检查弹体存在，还检查普通敌人和 Boss 的弹体是否真的被墙挡住、是否命中正确目标。

相关最终证据：敌人行走 31 项、实际导航 13 项、实际战斗和弹体遮挡 62 项、治疗反应 69 项/10 次真实治疗信号。数值对应各自日志，不合并成“所有 AI 情况均已覆盖”。

## 14. Boss 场地互动：把事件落到物理和状态变化

每个 Boss 的机制至少要回答六个问题：

1. 什么条件触发：入场、血量阈值、指定技能、玩家交互还是计时？
2. 预警是什么：玩家如何知道危险即将发生？
3. 哪些实体改变：碰撞、可破坏物、掩体、敌人、地板或灯光？
4. 实际效果是什么：伤害、遮挡、失衡、减速、引力还是裁决资格？
5. 怎样结束：计时、击破、交互、死亡或阶段改变？
6. 如何重试和重载：临时物是否清理，奖励是否重复，已完成事实是否保留？

独立边界由 [boss_encounter_boundary.gd](../../../game/scripts/world/boss_encounter_boundary.gd) 管理，实际场地对象与行为接入 [boss_arena_story_props.gd](../../../game/scripts/world/boss_arena_story_props.gd) 等控制器。普通受击、状态伤害和处决都应遵守共同入场/剧情阈值规则，不能只在某一种攻击里限制。

剧情物证和 NPC 迁移由实际拾取、牢门、精英死亡及对话完成决定。浏览器审计不直接赠送符文或修改库存来掩盖这些入口条件。

玄霄逃生还检查死亡后的 Continue：Boss 完成事实保留，逃生重试不重新发放战利品，钱包与可回收失烬合计 2250→2250。场景“能重启”和“重启不重复收益”是两项不同要求。

原生 Boss 机制 399 项、边界 568 项。Chrome 阶段预览通过生产 receive_hit 注入伤害，指定技能则启动真实攻击流程；这证明指定条件下的响应，不证明 AI 自主选择或手打击败八 Boss。完整阈值和证据见 [八 Boss 验收表](01-story-scene-encounters.md)。

## 15. UI：原生布局测试之后，仍要量真实 Web viewport

HUD 简化为生命/耐力/专注、余烬、三武器栏、地点和当前机关目标。装备、暂停、帮助和背包统一字体与主题，支持从不同入口打开并恢复原暂停状态和焦点。

但原生测试能主动设置 SubViewport 尺寸，不代表 Web 导出实际采用同一尺寸。Chrome 854×480 时，曾测到：

~~~text
浏览器窗口 / canvas = 854 × 480
Godot visible viewport / HUD root = 1280 × 720
~~~

项目使用 canvas_items 拉伸，HUD 的紧凑判断看到的仍是固定尺寸。改为 disabled，让实际窗口尺寸触发布局。修复后 854×480 和 390×844 的 HUD root 与真实 viewport 一致。

继续保持装备窗打开，从 854 缩到 390，又发现卡片图标只在创建时判断显示，缩窗后残留图标挤得中文竖排。将图标可见性移入 _layout 的动态处理，增加“打开状态缩窗”的回归，而不是仅测试每个尺寸重新打开菜单。

其他修复包括：

- 浅色天界地板上的武器提示缺乏背景对比，增加暗色底。
- 单 Boss 试炼错误显示“第 0 波”，只有真正波次试炼才显示波数，其他显示时间。
- 字体按实际界面文本生成中文子集；最新检查需要 1,677 个字符，零缺字。
- Web 安全区从 CSS 获取，避免用显示器尺寸计算浏览器伪边距。

最终 HUD 75 项；Chrome 目检装备窗打开时 854→390→854 的变化。[最终竖屏图](../../../build/story-campaign-20260910/chrome/equipment-portrait-resize-final.png)。

## 16. Chrome 首次启动：把空异常追到 Pointer Lock

正常入口首次出现“Uncaught (in promise)”且没有参数，单看控制台条目无法定位。刷新后消失也不能直接判定修好了，因为浏览器的用户交互和存储状态已经改变。

排查步骤：

1. 建立全新隔离上下文。
2. 在页面脚本运行之前监听 unhandledrejection，只记录 reason/name/message，不阻止错误。
3. 先等正常页面加载，再分别按 Enter 和 W。
4. 同时检查 GODOT_CONFIG.args、AshenAudit 是否存在、document.pointerLockElement 和控制台。

实际原因是 NotAllowedError: A user gesture is required to request Pointer Lock。

player._ready() 原来在网页刚启动时申请捕获鼠标，此时没有用户手势。修复为 Web 跳过 ready 捕获，只在未被 UI 消费的真实鼠标左键或 WASD InputEventKey 到达玩法输入处理时申请。测试工具注入的 InputEventAction 不用于触发浏览器鼠标捕获。

第一版补丁还有 GDScript bool 类型推导错误，原生测试未进入正常运行；保留失败日志，明确标注 bool 后重跑，不能把被终止进程的退出结果当作成功。

最终全新上下文：Enter 开始，W 移动后 pointerLocked=true，启动 rejection/error 都为空，正常页面 args=[]、没有 AshenAudit，实际 Chrome 控制台零 error/warn。

证据：[正常入口启动回执](../../../build/story-campaign-20260910/chrome/normal-fresh-start-pointer-lock-fixed.json)、[实际控制台查询](../../../build/story-campaign-20260910/chrome/normal-final-console.json)。

## 17. 如何组织验证，避免测试自己证明自己

### 17.1 三条相互补充的证据链

**资产链**：原始 GLB → Blender 绑定/生成 → staged → 独立文件验证 → Godot 实际导入 → 发布哈希。

**玩法链**：实际场景对象 → 生产交互/受击/移动入口 → 物理帧推进 → 观察状态、碰撞、导航和恢复。

**视觉链**：明确导出版本 → Chrome 真正加载 → 固定观察点或真实输入 → 连续画面和状态 → 修复后同条件复查。

不同链回答不同问题。Blender solid shading 图不是 PBR 游戏渲染验收；导航连通不是连续输入通关；手动写 complete=true 不是解谜；导出退出 0 不是浏览器已打开成功。

### 17.2 明确审计命令的能力和限制

browser_gameplay_audit.gd 只在显式 debug 审计入口启用，普通 index.html 保持无参数、无桥。

- level / visit：直接加载或摆位，必须标记 inspection。
- input：构造 InputEventAction，经生产输入处理，按物理帧按住并释放；不直接写速度。
- interact：使用真实扫描器选中的附近目标，校验距离、候选身份和对象有效性。
- boss_hit：调用生产受击入口，但伤害来自测试注入。
- boss_skill：指定真实技能流程，不代表 AI 自主选择。
- camera / time_scale：辅助观察，不直接 seek 身体动作。

冻结敌人的巡检图不能证明活动 AI。先运行 1.5 秒物理和动画再冻结，避免把未落地出生状态误认为场景问题，但真实战斗需另跑。

### 17.3 同时保存失败与成功

例如镜湖 JSON 保留未读镜尝试，迷宫保留旧出口受阻位置，UI 保存竖排反例，相机保留近墙和实际离墙后的图。

名称里有 final 或 restored，不足以证明状态正确。文档只引用对应状态真的恢复的证据；旧版本页面、失败日志和早期截图仍保留，但不计入最新通过项。

### 17.4 检查工具本身也会影响结果

旧审计器每 0.05 秒遍历整个世界并重复构造数据，可能拖慢被测游戏。改为 0.25 秒采样，缓存关卡列表和环境节点计数，并支持关闭自动采样；命令结束仍发布结果。

记录 snapshot 和 publish 耗时，用真实 RAF、引擎 FPS、WebGL renderer 做对照。观察到采样关闭前后约 25/27 FPS 的局部样本，不能据此宣布整场景性能优化完成；自动采样关闭后，旧快照里的 FPS 也会停在旧值，不能拿它当新测量。

## 18. 协作、工具故障与工作区处理

这次使用有界分工：资产/机关、Boss 机制、运行时接口/证据分别安排文件所有权，父代理负责共享文件、整合、引擎和 Chrome 验证。多代理可以并行读文件和写互不冲突的代码，但不同时操作同一个 Blender 场景、导入缓存或 Godot 运行目录。

具体做法：

- 显式交接 ENGINE FREE，再由下一执行者占用引擎；并行工作集中在独立源码审计或文档整理。
- 收到代理的“通过”后，仍读取日志、检查数值和运行范围；最终父代理再做必要的集成复核。
- 保留已有脏工作区，不 reset、不顺手回滚无关改动。
- Windows 后台进程只在确认属于当前任务时终止；原生测试脚本报错后可能不自行退出，需要结合日志判断。
- PowerShell 的搜索通配模式用 rg 的 -g 参数，避免把不存在的文字通配路径传给程序。
- Chrome 截图工具曾拒绝 filePath 写入，但返回了截图图像内容；使用返回的图像字节保存，再解码为 PNG。没有靠绕过审批完成截图写入。
- Godot parse/import 检查不能替代实际动态 load；只有真正加载脚本才能暴露的错误，要由对应契约执行发现。
- 本次文档整理只读取现有结果，没有为了增加“用过工具”的记录重新调用 Blender MCP。

后续继续开发时，最值得复用的是这个顺序：先核对真正运行的版本和文件，再把问题缩小到具体层；建立能复现故障的反例，只修改已确认导致问题的部分；用独立数据、真实物理和最终画面交叉确认；最后记录起点、输入方式、退出码、警告、文件哈希以及没有覆盖的范围。
